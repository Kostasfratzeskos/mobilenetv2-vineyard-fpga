## 1. Η μεγάλη εικόνα

### Πού ήμουν

Πριν από αυτή τη συνεδρία είχα **7 αριθμητικά engines** (`requantize`, `conv1x1`,
`bias_add`, `dwconv3x3`, `conv3x3_std`, `residual_add`, `avgpool`) — όλα επαληθευμένα
bit-exact απέναντι στα golden vectors. Είχα επίσης το `mac_lane` (μία «πλατιά» lane,
16 MAC/κύκλο) από τον Αύγουστο.

Το πρόβλημα: **τα engines ξέρουν μόνο να υπολογίζουν.** Κανένα δεν ξέρει *ποια* δεδομένα
να πάρει, από *πού*, και *πότε*. Αυτή τη δουλειά την έκαναν χειροκίνητα τα integration
testbenches με `for` loops. Αυτό που χτίστηκε τώρα είναι το hardware που κάνει τα ίδια —
δηλαδή ο controller.

### Πού είμαι τώρα

Ο pointwise δρόμος είναι **πλήρης από τους μετρητές μέχρι τους accumulators**:

```
                        ┌──────────────────────────────────────────┐
                        │              pw_feeder                   │
                        │                                          │
   start ──────────────►│  ┌────────────┐                          │
   n_pix, n_oc, n_ic ──►│  │  addr_gen  │  pix / oct / ict         │
   n_ent, base_in       │  │            │  valid / first / last    │
   stall ──────────────►│  └─────┬──────┘                          │
                        │        │                                 │
                        │        ├──► w_addr ──┐                   │
                        │        └──► a_addr ──┤                   │
                        │                      │                   │
   DMA (128 bit) ──────►│  ┌───────────────────▼───┐  4096 bit     │
                        │  │      wgt_buffer       │──────────┐    │
                        │  │  32 banks × 128 bit   │          │    │
                        │  └───────────────────────┘          │    │
                        │                                     ▼    │
                        │  ┌───────────────────────┐  128 ┌────────┴──┐
   writeback ──────────►│  │      act_buffer       │─────►│ pe_array  │
                        │  │  256-bit entries      │ bit  │ 32 lanes  │
                        │  └───────────────────────┘      │ =512 MAC  │
                        │                                 └─────┬─────┘
                        └───────────────────────────────────────┼─────┘
                                                                │
                                      acc[32] + acc_pix/acc_oct ▼
                                            (προς bias → requantize → writeback)
```

Ιεραρχία αρχείων:

```
pw_feeder.v                 ← hardware/rtl/control/
├── addr_gen.v              ← hardware/rtl/control/
├── wgt_buffer.v            ← hardware/rtl/control/
├── act_buffer.v            ← hardware/rtl/control/
└── pe_array.v              ← hardware/rtl/kernels/
    └── mac_lane.v ×32      ← hardware/rtl/kernels/
```

### Οι παράμετροι, και από πού ήρθαν

Πριν γραφτεί γραμμή RTL, στις 10/09 κλείδωσα δύο αποφάσεις **με μετρήσεις**, όχι με
διαίσθηση. Και οι δύο βγαίνουν από το `scripts/analyze_workload.py`, που ξαναδιαβάζει
το `manifest.json` και ξαναϋπολογίζει τα πάντα:

| | τιμή | πώς βγήκε |
|---|---|---|
| `Tm` (lanes) | **32** | DD-013: 92,1% utilization σε όλα τα 34 pointwise layers |
| `Tn` (taps/lane) | **16** | το ίδιο· το 64×8 έδινε μόλις 74,9% |
| `P` | 512 MAC/κύκλο | `Tm × Tn` |
| `ACC_W` | 21 bit | προϋπόθεση του datapath (βλ. §9) |

Διόρθωσα επίσης ένα λάθος νούμερο στο `controller_design.md`: τα βάρη είναι **2,19 MB**,
όχι 3,4 MB — το 3,4 είναι το MobileNetV2 του ImageNet, που έχει classifier 1280×1000
αντί για τον δικό μας 1280×4.

## 2. Η μέθοδος: γιατί εμπιστεύομαι ό,τι χτίστηκε

Αυτό είναι το πιο σημαντικό κομμάτι του εγγράφου, γιατί ισχύει για **όλα** τα modules.

### 2.1 Δύο oracles, όχι ένα

Ένα testbench που λέει «πέρασε» δεν αποδεικνύει τίποτα αν το ίδιο το testbench έχει το
ίδιο λάθος με το DUT. Γι' αυτό κάθε module συγκρίνεται με **δύο ανεξάρτητες πηγές
αλήθειας**:

1. **Ανεξάρτητο reference** υπολογισμένο μέσα στο testbench (σε `longint`, δηλαδή με
   εντελώς άλλη αριθμητική από το RTL).
2. **Ένα engine που έχει ήδη αποδειχθεί** — συνήθως το `conv1x1`, που κάνει 1 MAC/κύκλο
   και είναι επικυρωμένο απέναντι στα golden vectors από τον Ιούλιο.

Το ίδιο dot product τρέχει και στους δύο δρόμους και **τα τρία** αποτελέσματα πρέπει να
συμφωνούν. Αν το testbench είχε λάθος αριθμητική, το `conv1x1` θα διαφωνούσε. Αν το
`conv1x1` είχε λάθος, το reference θα διαφωνούσε.

### 2.2 Mutation testing: αποδεικνύω ότι το test *μπορεί* να αποτύχει

Αυτό είναι καινούργιο σε αυτή τη συνεδρία και είναι η πιο χρήσιμη συνήθεια που απέκτησα.

**Το πρόβλημα:** ένα test που περνάει μπορεί να περνάει επειδή το DUT είναι σωστό — ή
επειδή το test δεν κοιτάζει πουθενά. Δεν ξεχωρίζεις τα δύο βλέποντας ένα `PASS`.

**Η λύση:** σπάω **επίτηδες** το DUT και επιβεβαιώνω ότι το test το πιάνει. Αν δεν το
πιάσει, το test έχει τρύπα.

Τι βρήκε στην πράξη:

| module | μεταλλάξεις | πιάστηκαν |
|---|---:|---:|
| `pe_array` | 3 | **3** |
| `addr_gen` | 2 | **2** |
| `wgt_buffer` | 1 | **1** |
| `act_buffer` | 2 | **2** |
| `pw_feeder` | 3 | **2** ⚠️ |

Δύο περιπτώσεις αξίζει να τις θυμάμαι, γιατί διδάσκουν κάτι:

**(α) Στο `pe_array`**, έσπασα το activation broadcast (οι μονές lanes έβλεπαν άλλα
δεδομένα). Η περίπτωση «lane identity» — που έχει ομοιόμορφα βάρη ανά lane — **το
προσπέρασε τελείως**, γιατί όταν όλα τα βάρη μιας lane είναι ίδια, η σειρά των taps δεν
έχει σημασία. Το έπιασε μόνο η περίπτωση «one-hot tap». Αυτό δικαιολογεί γιατί υπάρχουν
**και οι δύο** περιπτώσεις, και είναι το είδος του συλλογισμού που θα αναφέρω στην
εξέταση.

**(β) Στο `pw_feeder`**, μία μετάλλαξη **δεν** πιάστηκε — και η διερεύνηση του γιατί
αποκάλυψε πραγματικό περιορισμό που δεν είχα γράψει πουθενά. Λεπτομέρειες στην §7.4.

## 3. `pe_array.v` — 32 lanes που μοιράζονται ένα broadcast

**Τι κάνει.** 32 αντίγραφα του `mac_lane`, καθένα υπολογίζει ένα κανάλι εξόδου.
Συνολικά 32 × 16 = **512 πολλαπλασιασμοί ανά κύκλο**.

**Η βασική ιδέα, σε μία πρόταση:** ένα 1×1 convolution χρησιμοποιεί **τα ίδια
activations** για κάθε κανάλι εξόδου. Άρα το `a` καλωδιώνεται σε **όλες** τις lanes, ενώ
κάθε lane κρατά τα δικά της βάρη.

```
                a[0..15]  (128 bit, ΚΟΙΝΟ σε όλες τις lanes)
       ┌───────────┼───────────┬─────── ... ───────┐
       ▼           ▼           ▼                   ▼
   ┌───────┐   ┌───────┐   ┌───────┐          ┌───────┐
   │ lane0 │   │ lane1 │   │ lane2 │   ...    │lane31 │
   │ w0[16]│   │ w1[16]│   │ w2[16]│          │w31[16]│   ← δικά της βάρη
   └───┬───┘   └───┬───┘   └───┬───┘          └───┬───┘
       ▼           ▼           ▼                   ▼
    acc[0]      acc[1]      acc[2]    ...      acc[31]
```

**Γιατί αυτή η ασυμμετρία έχει σημασία:** καθορίζει όλο το memory subsystem.

- activations: 16 bytes/κύκλο = **128 bit** → τετριμμένο, μία λέξη URAM
- βάρη: 32 × 16 bytes/κύκλο = **4096 bit** → αυτό είναι το δύσκολο

Όλος ο `wgt_buffer` (§5) υπάρχει για να λύσει αυτό το δεύτερο νούμερο.

**Ένα σημείο σχεδίασης:** το `done` το παίρνω από τη lane 0, δεν το ξαναφτιάχνω. Επειδή
όλες οι lanes βλέπουν τα ίδια `valid/first/last`, τρέχουν σε lockstep — και παίρνοντάς το
από πραγματική lane, μένει ευθυγραμμισμένο με το `acc` **εκ κατασκευής**, όχι κατά
σύμπτωση. Οι 31 αχρησιμοποίητοι done καταχωρητές κλαδεύονται στη σύνθεση.

**Το bus layout** (το κλειδί για όλα τα επόμενα):

```
w[(m*TN + j)*8 +: 8]   =  το βάρος της lane m για το κανάλι εισόδου j
```

Δηλαδή **oc-major / ic-minor** — που είναι *ακριβώς* η διάταξη `w[oc*IC + ic]` του
`manifest.json`. Αυτό δεν είναι σύμπτωση, το επέλεξα έτσι: σημαίνει ότι ο loader
αντιγράφει συνεχόμενο χώρο ανά lane, χωρίς καμία αναδιάταξη.

**Επαλήθευση:** 19 cases, 608 lane-checks. Οι directed cases δίνουν σε **κάθε lane και
κάθε tap ξεχωριστή τιμή**, ώστε οποιαδήποτε διασταύρωση καλωδίων να φαίνεται αμέσως.

## 4. `addr_gen.v` — οι μετρητές που αντικαθιστούν τα `for` loops

**Τι κάνει.** Παράγει την ακολουθία `(pixel, oc_tile, ic_tile)` με την οποία σαρώνεται
ένα layer, μαζί με τα `first`/`last` που ελέγχουν τον accumulator.

Ο βρόχος που υλοποιεί:

```
for pix in 0 .. n_pix-1              // H*W pixels εξόδου
  for oct in 0 .. n_oc-1             // ceil(OC/32) tiles καναλιών εξόδου
    for ict in 0 .. n_ic-1           // ceil(IC/16) tiles καναλιών εισόδου
      emit (pix, oct, ict)
      first = (ict == 0)             // → ο accumulator μηδενίζεται
      last  = (ict == n_ic-1)        // → το done πυροδοτεί τον επόμενο κύκλο
```

Αυτό είναι **κατά λέξη** ό,τι κάνει το `pointwise_layer_tb` με φωλιασμένα `for`. Ό,τι
έκανε το testbench σε χρόνο προσομοίωσης, το κάνει τώρα το hardware με μετρητές.

**Γιατί τα shapes είναι runtime inputs και όχι parameters:** ένα instance πρέπει να
εξυπηρετήσει και τα **34 pointwise layers**. Οι διαστάσεις θα έρχονται από το instruction
word του top sequencer (build plan #6). Αν ήταν parameters, θα χρειαζόμουν 34 instances.

**Πλάτη μετρητών** — μετρημένα, όχι εικασίες:

| μετρητής | μέγιστο στο δίκτυο | bits |
|---|---:|---:|
| `n_pix` | 12.544 (112×112) | 14 |
| `n_oc` | 40 (OC=1280) | 6 |
| `n_ic` | 80 (IC=1280, classifier) | 7 |

**Καμία λογική για tails, επίτηδες.** Όταν το OC ή το IC δεν διαιρείται με 32/16, δεν
υπάρχει ειδική μεταχείριση εδώ. Λύνεται εκεί που **φορτώνονται τα βάρη** (§8.2). Αυτό
κρατά τον address path καθαρό — και αφορά μόνο 5 από τα 34 layers.

**Επαλήθευση:** 35 layers. Το testbench κρατά τα `for` loops ως oracle και βαθμολογεί
κάθε tile **κύκλο προς κύκλο**. Κάθε shape τρέχει **δύο φορές** — ελεύθερα και με 35%
τυχαία stalls — και οι δύο ακολουθίες πρέπει να είναι ταυτόσημες. Καλύπτονται:

- τα πραγματικά shapes του δικτύου
- το εκφυλισμένο `1×1×1`, όπου `first` και `last` σηκώνονται στον **ίδιο** κύκλο
- layer μηδενικού μεγέθους (πρέπει να απορριφθεί, όχι να κρεμάσει)
- restart στη μέση ενός layer

Υπάρχει και **watchdog**: αν ένας μετρητής κολλήσει, το sim αποτυγχάνει αντί να κρεμάσει.
Αυτό φάνηκε χρήσιμο αμέσως — η μετάλλαξη με off-by-one στο `ict_wrap` θα κρεμούσε.

## 5. `wgt_buffer.v` — η απάντηση στα 4096 bit/κύκλο

**Το πρόβλημα.** Το `pe_array` καταναλώνει 512 int8 βάρη **κάθε κύκλο**. Καμία μνήμη δεν
δίνει 4096 bit/κύκλο.

**Η λύση.** 32 ανεξάρτητες τράπεζες των 128 bit, που διαβάζονται **με την ίδια
διεύθυνση**. Η τράπεζα `m` ταΐζει τη lane `m`.

```
              rd_addr (κοινή)
        ┌───────┬───────┬─── ... ───┐
        ▼       ▼       ▼            ▼
     bank0   bank1   bank2   ...  bank31      κάθε μία: DEPTH × 128 bit
        │       │       │            │
        └───────┴───────┴─── ... ────┘
                     │
                 4096 bit  →  pe_array.w
```

**Η ασυμμετρία θυρών είναι το ζουμί:**

| | πλάτος | γιατί |
|---|---|---|
| ανάγνωση | **4096 bit** | και οι 32 lanes πυροδοτούν μαζί |
| εγγραφή | **128 bit**, μία τράπεζα/κύκλο | ένα AXI-HP beat από το DDR |

Δεν έχει νόημα να κάνω την εγγραφή πλατιά: το DMA δίνει 128 bit τη φορά και τελεία. Το
φόρτωμα ενός layer κοστίζει `32 × entries` κύκλους και **επικαλύπτεται** με τον
υπολογισμό του προηγούμενου layer (double buffering).

**Η διεύθυνση δεν χρειάζεται πολλαπλασιαστή.** Η προφανής μορφή είναι
`rd_addr = oct*n_ic + ict`, αλλά η σειρά σάρωσης την κάνει γραμμική: τα tiles βγαίνουν
με τη σειρά `0, 1, 2, ..., n_oc*n_ic-1`. Άρα αρκεί **ένας μετρητής** που αυξάνεται σε
κάθε tile. Και επειδή ένα 1×1 conv ξαναχρησιμοποιεί τον **ίδιο** πίνακα βαρών σε κάθε
pixel, ο μετρητής απλώς **μηδενίζεται** στο τέλος κάθε pixel.

**Sizing** — από το `manifest.json`: το μεγαλύτερο layer είναι το `features.18.0`
(320→1280 στα 7×7), που θέλει `40 × 20 = 800` entries = **400 KB**. Με `DEPTH=1024`
υπάρχει περιθώριο και κοστίζει ~15 URAM.

**Επαλήθευση:** 9 checks. Το σημαντικότερο είναι ο έλεγχος **θέσης bit**: κάθε τριάδα
`(τράπεζα, διεύθυνση, tap)` παίρνει ξεχωριστή τιμή και ελέγχονται και τα 512 bytes κάθε
entry. Αν η σειρά των τραπεζών ή των taps ήταν λάθος, **κάθε dot product στο δίκτυο θα
ήταν σιωπηλά λάθος** — γι' αυτό αυτός ο έλεγχος είναι ο πιο σημαντικός του module.

> **Σημείωση ειλικρίνειας.** Ο πρώτος έλεγχος latency που έγραψα ήταν **λάθος δικό μου
> στο testbench**, όχι στο DUT: διάβαζε δύο φορές την ίδια διεύθυνση, οπότε «παλιά» και
> «νέα» τιμή ήταν εξ ορισμού ίδιες και ο έλεγχος πυροδοτούσε ψευδώς. Διορθώθηκε ώστε να
> «παρκάρει» πρώτα την έξοδο σε άλλη entry.

## 6. `act_buffer.v` — γιατί οι entries είναι 256 bit

Αυτό είναι το module με το πιο ενδιαφέρον εύρημα της συνεδρίας.

### 6.1 Η ανακάλυψη: αναντιστοιχία πλάτους

Ο array είναι **ασύμμετρος στις δύο κατευθύνσεις**:

- **γράφει** 32 κανάλια εξόδου τη φορά (ένα αποτέλεσμα `oc_tile`)
- **διαβάζει** 16 κανάλια εισόδου τη φορά (ένα `ic_tile`)

Αν η μνήμη ήταν 128 bit (16 bytes), κάθε writeback θα χρειαζόταν **2 κύκλους**. Συνήθως
δεν πειράζει, γιατί ο υπολογισμός διαρκεί `n_ic` κύκλους. Αλλά:

```
features.2.conv.0.0 :  IC=16  →  n_ic = ceil(16/16) = 1

  compute   : 12544 px × 3 oc_tiles × 1 = 37.632 κύκλοι
  writeback : 12544 px × 3 oc_tiles × 2 = 75.264 κύκλοι   ← κυριαρχεί!
```

**Ένα layer**, αλλά **+6,6% σε ολόκληρο το pointwise runtime** (568k κύκλοι συνολικά).
Και θα το ανακάλυπτα μόνο στο integration, ως ανεξήγητη επιβράδυνση.

### 6.2 Η λύση

Αποθηκεύω **32 κανάλια ανά entry** (256 bit) και κάνω mux στην πλευρά της ανάγνωσης:

```
entry (256 bit) = [ κανάλι 31 ][ ... ][ κανάλι 1 ][ κανάλι 0 ]
                   └──── sel=1 ────┘  └──── sel=0 ────┘
                      κανάλια 16-31      κανάλια 0-15
```

Άρα **δύο διαδοχικά `ic_tile` μοιράζονται μία entry**:

```
rd_addr = base_in + pix*ceil(IC/32) + (ict >> 1)
rd_sel  = ict[0]
```

Αποτέλεσμα: **μία εγγραφή ανά `oc_tile`, μία ανάγνωση ανά `ic_tile`**, και οι δύο σε ένα
κύκλο. Το πρόβλημα εξαφανίζεται.

Δουλεύει ομοιόμορφα και στις άβολες περιπτώσεις — τις οποίες έλεγξα ρητά:

| IC | entries | tiles | πώς αντιστοιχίζονται |
|---:|---:|---:|---|
| 96 | 3 | 6 | καθαρό: 2 tiles ανά entry |
| 24 | 1 | 2 | μία entry· το πάνω μισό είναι 8 πραγματικά + 8 padding |
| 48 | 2 | 3 | tiles 0,1 από entry 0· tile 2 από το **κάτω** μισό της entry 1 |
| 16 | 1 | 1 | μόνο το κάτω μισό χρησιμοποιείται |

### 6.3 Καθόλου ping-pong hardware

Το `controller_design.md` §4 λέει «activations on-chip με ping-pong». Ο προφανής τρόπος
είναι δύο σταθερά μισά. Το μέτρησα:

- δύο σταθερά μισά = **2× το μεγαλύτερο feature map** = 2,3 MB
- αυτό που *πραγματικά* χρειάζεται = το μεγαλύτερο **ζεύγος input+output** που πρέπει να
  συνυπάρχει = **1,53 MB**

Άρα: **μία επίπεδη δεξαμενή**, και το ping-pong γίνεται δύο base-address καταχωρητές
στον sequencer. Λιγότερο hardware *και* λιγότερη μνήμη — και ταιριάζει με την αρχή που
ακολουθώ παντού: **χαζό hardware, πολιτική στον controller**.

> **Παρεμπιπτόντως:** το μεγαλύτερο tensor βγαίνει τυπικά η είσοδος 224×224×3 (1,53 MB),
> αλλά μόνο επειδή 3 κανάλια γεμίζουν entry των 32 και σπαταλούν 91%. Η εικόνα εισόδου
> **δεν** περνά από τον pointwise array — την καταναλώνει ο stem, με δικό του layout.
> Γι' αυτό δεν μετράει εδώ.

**Επαλήθευση:** 8 checks, με κεντρικό test το «layer replay»: γράφω ένα feature map όπως
θα το έγραφε ο array, το διαβάζω όπως θα το διαβάσει ο `addr_gen` του επόμενου layer, και
ελέγχω **κάθε κανάλι κάθε tile**.

## 7. `pw_feeder.v` — η κόλλα, και εκεί που ζουν τα δύσκολα

### 7.1 Το pipeline

Αυτό είναι το πιο λεπτό σημείο όλου του build plan #3.

```
κύκλος C     addr_gen βγάζει (pix, oct, ict) + valid/first/last
             → υπολογίζονται οι διευθύνσεις, εκδίδονται οι αναγνώσεις

κύκλος C+1   τα δεδομένα των buffers φτάνουν
             τα valid/first/last, ΚΑΘΥΣΤΕΡΗΜΕΝΑ ΚΑΤΑ ΕΝΑ, φτάνουν στο pe_array
             μαζί με τα δεδομένα

κύκλος C+2   το acc του pe_array είναι τελικό και το done είναι ψηλά
```

**Γιατί η καθυστέρηση είναι υποχρεωτική:** οι buffers έχουν registered έξοδο, άρα
απαντούν έναν κύκλο αργότερα. Αν τα `valid/first/last` έφταναν στον array **μαζί** με τη
διεύθυνση (δηλαδή έναν κύκλο νωρίς), τότε:

- το `first` θα μηδένιζε τον accumulator στο **λάθος** tile
- κάθε dot product στο δίκτυο θα ήταν **κοντό κατά έναν όρο**
- και θα έβγαζε ακόμα **εύλογους** αριθμούς — το χειρότερο είδος bug

Γι' αυτό το mutation test A ήταν το πιο σημαντικό: αφαίρεσα την καθυστέρηση και
επιβεβαίωσα ότι πιάνεται.

### 7.2 Γιατί υπάρχουν τα tags

Το `done` φτάνει **δύο κύκλους** μετά το tile που το προκάλεσε. Ως τότε ο `addr_gen`
έχει προχωρήσει. Άρα: **ποιο στοιχείο εξόδου** είναι αυτά τα 32 αποτελέσματα;

Λύση: το `(pix, oct)` ταξιδεύει παράλληλα, σε δικό του pipeline, και παρουσιάζεται μαζί
με το αποτέλεσμα ως `acc_pix` / `acc_oct`. Ο writeback ξέρει έτσι πού να τα γράψει.

Κρίσιμη λεπτομέρεια: **κάθε στάδιο του tag pipeline προχωρά με το δικό του `valid`**, όχι
με το γυμνό ρολόι. Αλλιώς ένα stall θα γλιστρούσε τα tags μπροστά από τα δεδομένα.

### 7.3 Διευθύνσεις χωρίς πολλαπλασιαστές

Οι προφανείς μορφές θέλουν δύο πολλαπλασιασμούς:

```
wgt_addr = oct * n_ic + ict
act_addr = pix * n_ent + (ict >> 1)
```

Κανένας δεν χρειάζεται, γιατί η σειρά σάρωσης τους κάνει γραμμικούς:

**Βάρη:** η σειρά των tiles **είναι** η σειρά διευθύνσεων, και επανεκκινεί σε κάθε pixel
(ένα 1×1 conv ξαναχρησιμοποιεί τον ίδιο πίνακα βαρών παντού). → ένας μετρητής που
αυξάνεται ανά tile και μηδενίζεται στο τέλος του pixel.

**Activations:** μόνο το `pix` κλιμακώνεται. → ένας base καταχωρητής που **προσθέτει**
`n_ent` όταν προχωρά το pixel, συν το `ict>>1` ως offset.

Αυτό δεν είναι μικροβελτιστοποίηση: ένας πολλαπλασιαστής στο κρίσιμο address path θα
κόστιζε DSP και, χειρότερα, θα δυσκόλευε το timing closure στα 250 MHz.

### 7.4 Η μετάλλαξη που δεν πιάστηκε — και τι αποκάλυψε

Από τις 3 μεταλλάξεις, οι 2 πιάστηκαν. Η τρίτη — **tag pipeline που προχωρά χωρίς
φρουρούς** — πέρασε ολόκληρο το testbench.

**Γιατί:** ο `addr_gen` **παγώνει** τις εξόδους του όταν το `valid` πέσει. Άρα το να
καταγράφεις το tag ανεπιφύλακτα δίνει την **ίδια** τιμή. Οι φρουροί είναι περιττοί *μέσα
σε ένα layer*.

**Πού ΔΕΝ είναι περιττοί:** στο πέρασμα από layer σε layer. Και ψάχνοντας αυτό, βρήκα
πραγματικό περιορισμό που δεν είχα γράψει πουθενά:

> Το `layer_done` πυροδοτεί όταν ο `addr_gen` **καταναλώνει** το τελευταίο tile — αλλά το
> αποτέλεσμα αυτού του tile είναι ακόμα **δύο στάδια πίσω**. Ένα `start` πριν αδειάσει το
> pipeline μηδενίζει τα `v_d/f_d/l_d` και αυτά τα αποτελέσματα **χάνονται** — δεν
> κακο-ετικετάρονται, χάνονται.

Το μέτρησα: τα αποτελέσματα συνεχίζουν να έρχονται **1 κύκλο** μετά το `layer_done`. Ο
sequencer πρέπει να αφήνει τουλάχιστον 2 κύκλους κενό — που δεν κοστίζει τίποτα, αφού
πρέπει να ξαναφορτώσει τον weight buffer στο μεταξύ.

Το testbench τώρα **μετράει** αυτό το drain latency και αποτυγχάνει αν μεγαλώσει.

**Το μάθημα:** μια μετάλλαξη που δεν πιάνεται δεν σημαίνει πάντα «κακό test». Εδώ
σήμαινε «ο κώδικας έχει άμυνα για κατάσταση που δεν έχω δοκιμάσει» — και η διερεύνηση
παρήγαγε τεκμηρίωση αντί για διόρθωση.

### 7.5 Επαλήθευση

17 checks. Το testbench γεμίζει τους buffers **όπως θα έκαναν το DMA και το προηγούμενο
layer**, πατάει start, και ελέγχει κάθε αποτέλεσμα — **τιμές και tag, με τη σειρά** —
απέναντι σε software dot product:

- καθαρά shapes (`IC32/OC64`, `IC96/OC32`, `IC64/OC96`)
- tails σε **κάθε** διάσταση (`IC24/OC24`, `IC96/OC24`, `IC40/OC64`)
- η περίπτωση `n_ic=1`, όπου `first` και `last` συμπίπτουν
- μη-μηδενικό `base_in`
- **και όλα ξανά με 30% τυχαία stalls**

## 8. Οι τρεις συμβάσεις που κρατούν το σύστημα σωστό

Αυτές είναι οι ρυθμίσεις που δεν φαίνονται στον κώδικα ενός module αλλά **πρέπει** να
τηρούνται από όλους. Αν σπάσει μία, το δίκτυο βγάζει λάθος αριθμούς χωρίς κανένα σφάλμα.

### 8.1 Bus layout contract

```
w  [(m*TN + j)*8 +: 8]   →  lane m, κανάλι εισόδου j     (oc-major / ic-minor)
acc[ m*ACC_W    +: ACC_W] →  το αποτέλεσμα της lane m
```

Ταυτίζεται με τη διάταξη `w[oc*IC + ic]` του `manifest.json`, ώστε ο `wgt_buffer` να
συνδέεται απευθείας στο `pe_array` **χωρίς αναδιάταξη**.

### 8.2 Tail contract — και γιατί οι δύο μισές του εξαρτώνται μεταξύ τους

Όταν το OC δεν διαιρείται με 32 ή το IC με 16, υπάρχουν «ψεύτικες» lanes και taps.

**Πλευρά βαρών:** ο loader γράφει πάντα **ολόκληρο** το ορθογώνιο `n_oc × n_ic` σε όλες
τις τράπεζες, με **μηδενικά** όπου δεν υπάρχει πραγματικό βάρος. Οι τράπεζες είναι και
zero-initialised, ώστε μια σύντομη φόρτωση να μην διαρρεύσει βάρη του προηγούμενου layer.

**Πλευρά activations — εδώ είναι το λεπτό σημείο:** όταν το OC έχει tail, ο array
παράγει και πάλι 32 αποτελέσματα, και οι padded lanes **δεν βγάζουν μηδέν**. Ο
accumulator τους είναι 0, αλλά μετά περνά από `bias_add` (προσθέτει bias ανύπαρκτου
καναλιού) και `requantize`. Άρα αποθηκεύονται **σκουπίδια**.

Αυτό είναι ακίνδυνο — **αλλά μόνο** επειδή το επόμενο layer πολλαπλασιάζει αυτά τα
κανάλια με βάρη που το contract των βαρών εγγυάται μηδενικά.

> **Άρα: οι δύο μισές του tail contract εξαρτώνται η μία από την άλλη. Δεν μπορεί να
> χαλαρώσει καμία μόνη της.** Το έγραψα και στα δύο modules.

### 8.3 Drain constraint

Ο sequencer πρέπει να αφήνει **≥2 κύκλους** μετά το `layer_done` πριν το επόμενο `start`,
αλλιώς χάνονται τα αποτελέσματα που είναι ακόμα στο pipeline (§7.4).

## 9. Τι ΔΕΝ έχει επαληθευτεί

Σημαντικό να είμαι ακριβής εδώ, γιατί εύκολα ξεχνιέται.

**Δεν έχει γίνει integration απέναντι στα golden vectors.** Όλα τα testbenches αυτής της
συνεδρίας χρησιμοποιούν **συνθετικά τυχαία δεδομένα** και reference dot products. Το
πραγματικό bit-exact test απέναντι στα `software/golden/` είναι το build plan #4.

**Όλα τρέχουν με `ACC_W=32`, όχι 21.** Τα testbenches χρησιμοποιούν 32-bit accumulator
ώστε τα τυχαία int8 δεδομένα πλήρους εύρους να μην υπερχειλίζουν. Το πραγματικό datapath
είναι **21 bit**, και αυτό είναι **προϋπόθεση, όχι απόδειξη**:

```
χειρότερη περίπτωση (IC=960):  960 × 128 × 127 = 15.605.760  → θέλει 25 bit
εύρος 21 bit signed:           −1.048.576 … +1.048.575
```

Στην πράξη δεν σκάει, επειδή τα activations μετά από ReLU6 είναι μικρά και τα πρόσημα
αλληλοαναιρούνται — και τα integration testbenches του Ιουλίου το επιβεβαιώνουν σε
πραγματικά δεδομένα. **Όταν κάνω το #4, να βάλω assertion υπερχείλισης.**

**Δεν έχει γίνει σύνθεση.** Δεν ξέρω ακόμα αν κλείνει το timing στα 250 MHz, ούτε τους
πραγματικούς πόρους. Το fanout του activation broadcast σε 32 lanes είναι ο ύποπτος.

**Δεν υπάρχει output path.** Το `capture → bias_add → requantize → writeback` δεν έχει
γραφτεί. Ο feeder βγάζει ακατέργαστους accumulators.

**Το cycle model είναι ιδανικό.** Μετράει tail-padding και τίποτε άλλο: δεν μοντελοποιεί
pipeline fill/drain, DMA stalls, ούτε μεταβάσεις layer.

## 11. Τι ακολουθεί

**Build plan #4 — το output half και το πραγματικό integration:**

1. `capture` — τα 32 acc σε shadow register, ώστε ο array να συνεχίσει αμέσως
2. `bias_add` + `requantize` ανά κανάλι → int8
3. writeback 256 bit στον `act_buffer` στη διεύθυνση που λένε τα `acc_pix`/`acc_oct`
4. integration απέναντι στο ίδιο golden που χρησιμοποιεί το `pointwise_layer_tb`, αλλά
   στα 512 MAC/κύκλο και με `ACC_W=21`

**Η απόφαση που θα θέλει νούμερα** (όπως το Tm/Tn): **πόσες παράλληλες μονάδες
requantize**. Ο array βγάζει 32 τιμές κάθε `n_ic` κύκλους. Με `R` μονάδες το άδειασμα
παίρνει `ceil(32/R)` κύκλους, που επικαλύπτεται με τον υπολογισμό — άρα δεν υπάρχει stall
όσο `ceil(32/R) ≤ n_ic`. Αλλά υπάρχει layer με `n_ic=1`, και κάθε μονάδα κοστίζει ~2 DSP
(πολλαπλασιασμός 21×32 bit). Να μετρηθεί το κόστος stall για `R ∈ {4, 8, 16, 32}` πριν
αποφασίσω.
